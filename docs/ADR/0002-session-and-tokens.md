# ADR-0002 — توکن دسترسی کوتاه‌عمر + refresh چرخشی

**وضعیت:** پذیرفته‌شده و پیاده‌سازی‌شده (تسک E1-04)

## زمینه

ورود با OTP است. کاربر باید «خروج از این دستگاه» و «خروج از همه‌ی دستگاه‌ها» داشته باشد،
مدیر باید بتواند نشست یک حساب مشکل‌دار را ببندد، و سرقت توکن باید **قابل تشخیص** باشد
(معیار پذیرش E1-04). نسخه‌ی اول با توکن مات سمت سرور نوشته شد؛ این ADR آن را جایگزین می‌کند.

## تصمیم

| توکن    | شکل                                             | عمر      | نگهداری                                              |
| ------- | ----------------------------------------------- | -------- | ---------------------------------------------------- |
| Access  | JWT HS256 (`sub`, `role`, `iat`, `exp`, `iss`)  | ۱۵ دقیقه | بی‌حالت، فقط امضا بررسی می‌شود                       |
| Refresh | رشته‌ی تصادفی ۲۵۶ بیتی، **فقط هش** ذخیره می‌شود | ۳۰ روز   | جدول `refresh_tokens` با `family_id` و `replaced_by` |

- هر بار refresh، توکن قبلی باطل و توکنی تازه در **همان family** صادر می‌شود (rotation).
- اگر توکنی که قبلاً چرخیده شده دوباره ارائه شود، یعنی لو رفته: **کل family باطل** می‌شود
  (`auth.refresh_reuse_detected` در audit) و هر دو طرف بیرون می‌مانند.
- باطل‌شدن عمدی (logout) با چرخش قابل تفکیک است: اگر `replaced_by` خالی باشد، logout است و
  فقط `REFRESH_TOKEN_INVALID` برمی‌گردد، نه هشدار سرقت.
- دسترسی هر درخواست: امضای JWT + **خواندن دوباره‌ی کاربر**؛ بنابراین تغییر نقش یا
  تعلیق حساب **بلافاصله** اثر می‌کند، نه بعد از انقضای توکن.
- RBAC به‌شکل `requireRole('ADMIN','OWNER')` (معادل decorator) در `src/http/roles.ts`.

## پیامدها

- تشخیص سرقت، خروج از همه‌ی دستگاه‌ها و دستگاه‌های ثبت‌شده (برای Push) فراهم است.
- هزینه: یک کوئری سبک برای کاربر در هر درخواست + یک نوشتن در هر refresh.
- اگر روزی ناوگان API بدون DB مشترک لازم شد، می‌توان `authenticate` را به اعتماد کامل به
  claims کاهش داد (با پذیرش تأخیر در ابطال).
